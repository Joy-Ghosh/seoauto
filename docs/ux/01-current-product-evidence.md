# What SEO Workbench actually does today

Date: 27 November 2026. Method: source inspection of the existing application in the earlier Codex workspace. This is a product capability audit, not customer research, a security certification or a new browser test. `J:\seoauto` did not contain the application when this audit began. The old Graphify snapshot is useful for orientation but does not establish the latest UI behavior.

## Product in one sentence

SEO Workbench is a private, evidence-led workspace for reading a website, reviewing possible problems, preparing selected fixes and checking a later response. It already has much of a **find → understand → draft → apply elsewhere → verify** loop. It is not yet a general public SEO platform or an automatic publisher.

That loop is a candidate product focus, not a validated claim about market demand. No customer interviews, adoption, retention, revenue or task-completion measurements were supplied for this audit.

## Where the current loop breaks

1. **One plan cannot yet hold every promised type of improvement.** The problem assistant can generate H1 text, but its save control only supports title, description and alt. Schema and internal-link advice likewise remain report material. A person can understand a useful change but cannot manage it consistently through the plan. Next design decision: define a shared proposed-change record with field-specific review/verification requirements before expanding copy or buttons. [assistant save behavior](C:/Users/joygh/Documents/Codex/2026-11-26/use-this-skill-install-it-https/outputs/seo-workbench/src/ProblemAssistant.tsx:18)

2. **GSC insight and AI generation are adjacent rather than connected.** GSC data is saved under a per-host browser key. `AiStudio.run()` sends scan/task/seeds/market/language/audience/question/page/competitor URLs; `buildContext()` packages scan evidence and competitor pages, not the GSC dataset. The current AI cannot honestly claim to analyze imported search performance automatically. Next decision: explicit selection and consent for dated GSC evidence, preserving query-page associations only when supplied. [GSC storage](C:/Users/joygh/Documents/Codex/2026-11-26/use-this-skill-install-it-https/outputs/seo-workbench/src/SearchConsolePanel.tsx:10), [AI request](C:/Users/joygh/Documents/Codex/2026-11-26/use-this-skill-install-it-https/outputs/seo-workbench/src/AiStudio.tsx:258), [AI context](C:/Users/joygh/Documents/Codex/2026-11-26/use-this-skill-install-it-https/outputs/seo-workbench/server/ai.ts:139)

3. **Lexical links can look more precise than their editorial value warrants.** Candidate generation loops over successful source pages with no privacy/legal-page exclusion. A brand-name overlap can make a privacy or terms paragraph eligible as a donor. The exact anchor and attractive connected card do not repair that selection weakness. Next decision: default-exclude legal/utility donors from editorial recommendations, disclose the exclusion and allow an expert override; require meaningful topic/intent evidence beyond brand overlap. [selection conditions](C:/Users/joygh/Documents/Codex/2026-11-26/use-this-skill-install-it-https/outputs/seo-workbench/server/audit.ts:351)

4. **JSON-LD count is thin evidence for schema advice.** The parser counts blocks; the AI context receives the count rather than the parsed existing entities and properties. “Improve schema” therefore needs a visible prerequisite: inspect existing markup and visible supporting facts. Next decision: distinguish “markup present” from “valid,” “eligible” or “complete.” [count](C:/Users/joygh/Documents/Codex/2026-11-26/use-this-skill-install-it-https/outputs/seo-workbench/server/audit.ts:85), [AI pack](C:/Users/joygh/Documents/Codex/2026-11-26/use-this-skill-install-it-https/outputs/seo-workbench/server/ai.ts:94)

5. **The experience is organized partly around tools and scans rather than a durable change.** Navigation separates Start, Website audit, AI tools and Saved changes; audit subviews add seven more choices. Drafts use `repairs:<scan-id>`. A user must maintain the relationship between baseline, draft, manual publishing and verification. Next decision: design a task-owned evidence trail that survives re-scans and exposes one primary next action. This is a source-grounded UX hypothesis, not an observed usability failure. [views/navigation](C:/Users/joygh/Documents/Codex/2026-11-26/use-this-skill-install-it-https/outputs/seo-workbench/src/main.tsx:53), [draft persistence](C:/Users/joygh/Documents/Codex/2026-11-26/use-this-skill-install-it-https/outputs/seo-workbench/src/main.tsx:187)

## Implications for the next MVP definition

The strongest existing unit of value is **one reviewed, implementable change with an inspectable before/after record**. Prioritize that loop before broadening research tools. Keep four different questions separate in every opportunity: What was observed? Why might it matter? How strong is the recommendation? What can verify the implementation?

Evidence confidence, editorial confidence, priority, implementation risk and expected business value are different attributes. None is currently a calibrated probability. Retain source/date/coverage in the card, make missing evidence actionable, and offer “review intentionally / not applicable” without implying that every heuristic needs a fix.

Success measures still need collection: first useful finding understood, first approved plan item, published change verified, return to a saved task, and explanations understood correctly. Any target for these is a design target until measured with representative users.
